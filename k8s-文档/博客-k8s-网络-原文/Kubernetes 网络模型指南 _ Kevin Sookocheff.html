Kubernetes 网络模型指南

2018年7月11日 · 33 分钟 · 凯文·苏科切夫

Kubernetes 的设计初衷就是为了在机器集群上运行分布式系统。分布式系统的本质决定了网络是 Kubernetes 部署的核心且必不可少的组成部分，理解 Kubernetes 网络模型将有助于您正确地运行、监控和排查在 Kubernetes 上运行的应用程序的问题。

网络领域是一个庞大的分支，拥有众多成熟的技术。对于不熟悉网络的人来说，这可能会令人感到困惑，因为大多数人对网络都有一些先入为主的观念，而要理解并整合大量新旧概念，并将其融会贯通，并非易事。例如，网络命名空间、虚拟接口、IP转发和网络地址转换等技术就属于此类。本指南旨在通过讨论Kubernetes的各项依赖技术，并阐述这些技术如何用于实现Kubernetes网络模型，从而揭开Kubernetes网络的神秘面纱。

本指南篇幅较长，分为多个章节。首先，我们将讨论一些基本的 Kubernetes 术语，以确保指南中所有术语的使用正确无误。然后，我们将讨论 Kubernetes 网络模型及其相关的设计和实现决策。接下来是本指南最长也是最精彩的部分：我们将深入探讨 Kubernetes 内部的流量路由方式，并列举几个不同的用例。

如果您对任何网络术语不熟悉，本指南附有网络术语表。

1 Kubernetes基础知识#

Kubernetes 由几个核心概念构建而成，这些概念不断组合，最终形成越来越强大的功能。本节列出了这些概念，并提供简要概述，以方便后续讨论。Kubernetes 的功能远不止此处列出的这些，但本节旨在作为入门指南，帮助读者理解后续章节的内容。如果您已经熟悉 Kubernetes，可以跳过本节。

1.1 Kubernetes API 服务器#

在 Kubernetes 中，所有操作都是通过 API 调用完成的，由Kubernetes API 服务器提供服务。APIkube-apiserver服务器是通往 etcd数据存储的网关，该数据存储维护着应用程序集群的期望状态。要更新 Kubernetes 集群的状态，您需要向 API 服务器发出 API 调用，描述您期望的状态。

1.2 控制器#

控制器是构建 Kubernetes 的核心抽象层。一旦你使用 API 服务器声明了集群的期望状态，控制器就会持续监控 API 服务器的状态并对任何变化做出反应，以确保集群的当前状态与期望状态一致。控制器使用一个简单的循环来运行，该循环不断检查集群的当前状态是否与期望状态一致。如果存在任何差异，控制器会执行相应的任务以使当前状态与期望状态保持一致。伪代码如下：

while true:
  X = currentState()
  Y = desiredState()

  if X == Y:
    return  # Do nothing
  else:
    do(tasks to get to Y)

例如，当您使用 API 服务器创建一个新的 Pod 时，Kubernetes 调度器（一个控制器）会感知到这一变化，并决定将 Pod 放置在集群中的哪个位置。然后，它会使用 API 服务器（由 etcd 提供支持）写入该状态变更。kubelet接下来，调度器（另一个控制器）会感知到这一新变化，并设置必要的网络功能，以确保 Pod 在集群中可访问。在这里，两个不同的控制器分别响应两个不同的状态变更，从而使集群的实际情况与用户的意图相符。

1.3 Pods#

Pod 是 Kubernetes 的基本单元——构建应用程序的最小可部署对象。一个 Pod 代表集群中正在运行的工作负载，它封装了一个或多个 Docker 容器、所需的存储以及一个唯一的 IP 地址。组成 Pod 的容器被设计为位于同一台机器上并进行调度。

1.4 节点#

节点是运行 Kubernetes 集群的机器。它们可以是裸机、虚拟机或其他任何类型的机器。“主机”一词经常与“节点”互换使用。我将尽量保持一致地使用“节点”一词，但有时也会根据上下文使用“虚拟机”来指代节点。

2 Kubernetes 网络模型#

Kubernetes 对 Pod 的联网方式有自己独特的见解。具体来说，Kubernetes 对任何网络实现都规定了以下要求：

  • 所有 Pod 都可以与其他所有 Pod 通信，而无需使用网络地址转换(NAT)。
  • 所有节点都可以与所有 Pod 通信，无需 NAT。
  • Pod 看到的自己的 IP 地址与其他设备看到的 IP 地址相同。

鉴于这些限制条件，我们剩下四个不同的网络问题需要解决：

  1. 容器间网络
  2. Pod 间网络连接
  3. Pod到Service的网络连接
  4. 互联网服务网络

本指南的其余部分将依次讨论这些问题及其解决方案。

3. 容器间网络#

通常，我们将虚拟机中的网络通信视为直接与以太网设备交互，如图 1 所示。

实际上，情况远比这复杂。在 Linux 系统中，每个运行的进程都在一个网络命名空间内进行通信，该命名空间提供了一个逻辑网络协议栈，其中包含自身的路由、防火墙规则和网络设备。本质上，网络命名空间为命名空间内的所有进程提供了一个全新的网络协议栈。

作为 Linux 用户，可以使用ip命令创建网络命名空间。例如，以下命令将创建一个名为 `<network_namespace_name>` 的新网络命名空间ns1。

$ ip netns add ns1

创建命名空间时，会在 下创建一个挂载点 /var/run/netns，即使没有进程附加到该命名空间，也能使其持久存在。

您可以通过列出 下的所有挂载点来列出可用的命名空间 /var/run/netns，或者使用ip命令。

$ ls /var/run/netns
ns1
$ ip netns
ns1

默认情况下，Linux 将每个进程分配到根网络命名空间，以便访问外部世界，如图 2 所示。

在 Docker 架构中，Pod 被建模为一组共享网络命名空间的 Docker 容器。Pod 内的所有容器都拥有相同的 IP 地址和端口空间，这些地址和端口空间通过分配给 Pod 的网络命名空间分配，并且由于它们位于同一命名空间中，因此可以通过 localhost 相互找到。我们可以在虚拟机上为每个 Pod 创建一个网络命名空间。这在 Docker 中是通过“Pod 容器”实现的，该容器会保持网络命名空间的打开状态，而“应用容器”（用户指定的容器）则通过 Docker 的 `--net=container` 参数加入该命名空间。ctr*函数。图 3 显示了每个 Pod 如何由共享命名空间内的多个 Docker 容器组成。

4. Pod 间联网#

在 Kubernetes 中，每个 Pod 都有一个真实的 IP 地址，并且每个 Pod 都使用该 IP 地址与其他 Pod 通信。当前的任务是了解 Kubernetes 如何使用真实 IP 地址实现 Pod 之间的通信，无论 Pod 部署在集群中的同一物理节点还是不同节点上。为了避免跨节点通信时通过内部网络带来的复杂性，我们首先讨论位于同一台机器上的 Pod。

从 Pod 的角度来看，它存在于自己的以太网命名空间中，需要与同一节点上的其他网络命名空间通信。幸运的是，命名空间可以通过 Linux虚拟以太网设备 ( VEED)或veth 对连接 。veth 对由两个虚拟接口组成，可以跨越多个命名空间。要连接 Pod 的命名空间，我们可以将 veth 对的一端分配给根网络命名空间，另一端分配给 Pod 的网络命名空间。每个 veth 对就像一根网线，连接两端并允许流量在它们之间流动。这种设置可以复制到机器上任意数量的 Pod。图 4 显示了将虚拟机上的每个 Pod 连接到根命名空间的 ve​​th 对。

此时，我们已经为每个 Pod 设置了各自的网络命名空间，使它们认为自己拥有独立的以太网设备和 IP 地址，并且它们都连接到节点的根命名空间。现在，我们希望 Pod 通过根命名空间相互通信，为此我们使用网络桥接器。

Linux 以太网桥接器是一种虚拟的二层网络设备，用于连接两个或多个网段，并以透明的方式将两个网络连接在一起。该桥接器通过维护源地址和目标地址之间的转发表来工作，它会检查流经桥接器的数据包的目标地址，并决定是否将数据包转发到连接到该桥接器的其他网段。桥接代码通过检查网络中每个以太网设备的唯一 MAC 地址来决定是否桥接数据或丢弃数据。

网桥实现 ARP协议来发现与给定IP地址关联的链路层MAC地址。当网桥收到数据帧时，它会将该帧广播给所有连接的设备（原始发送方除外），并将响应该帧的设备信息存储在查找表中。以后具有相同IP地址的流量会使用该查找表来发现正确的MAC地址，并将数据包转发到该MAC地址。

如图 6 所示，Pod 1 向其自身的以太网设备发送数据包eth0，该设备是 Pod 的默认设备。Pod 1eth0通过虚拟以太网设备连接到根命名空间veth0 (1)。该网桥cbr0配置了veth0一个附加到其上的网段。数据包到达网桥后，网桥veth1使用 ARP 协议 (3) 解析出要将数据包发送到的正确网段。当数据包到达虚拟设备时veth1，它被直接转发到 Pod 2 的命名空间以及该命名空间内的设备 (4)。在整个流量过程中，每个 Pod 都只与一个虚拟设备eth0通信，并且流量被路由到正确的 Pod。这种网络使用体验符合开发人员的预期。eth0localhost

Kubernetes 的网络模型规定，Pod 必须能够通过其 IP 地址跨节点访问。也就是说，网络中其他 Pod 始终可以看到一个 Pod 的 IP 地址，并且每个 Pod 看到的自己的 IP 地址与其他 Pod 看到的相同。现在我们来讨论如何在不同节点上的 Pod 之间路由流量的问题。

4.2 数据包的生命周期：Pod 到 Pod，跨节点#

在解决了同一节点上 Pod 之间的数据包路由问题后，我们接下来要解决不同节点上 Pod 之间的流量路由问题。Kubernetes 网络模型要求 Pod IP 地址在网络中可访问，但并未具体说明如何实现这一点。实际上，这取决于具体的网络环境，但一些最佳实践可以简化这一过程。

通常，集群中的每个节点都会被分配一个 CIDR 块，用于指定运行在该节点上的 Pod 可用的 IP 地址。一旦发往该 CIDR 块的流量到达节点，节点就负责将流量转发到正确的 Pod。图 7 展示了两个节点之间的流量流向，假设网络能够将 CIDR 块中的流量路由到正确的节点。

图 7 的初始请求与图 6 相同，不同之处在于，目标 Pod（绿色高亮显示）与源 Pod（蓝色高亮显示）位于不同的节点上。数据包首先通过 Pod 1 的以太网设备发送，该设备与根命名空间中的虚拟以太网设备配对 (1)。最终，数据包到达根命名空间的网络桥接器 (2)。由于桥接器上没有连接到具有正确 MAC 地址的设备，ARP 请求将失败。失败后，桥接器会将数据包通过默认路由——即根命名空间的eth0设备——发送出去。此时，路由离开节点并进入网络 (3)。我们假设网络可以根据分配给节点的 CIDR 块将数据包路由到正确的节点 (4)。数据包进入目标节点（eth0位于 VM 2 上）的根命名空间，并通过桥接器路由到正确的虚拟以太网设备 (5)。最后，路由通过位于 Pod 4 命名空间内的虚拟以太网设备对 (6) 完成。一般来说，每个节点都知道如何将数据包分发到其内部运行的 Pod。数据包到达目标节点后，其流向与同一节点上不同 Pod 之间路由流量相同的方式。

我们巧妙地避开了如何配置网络以将 Pod IP 的流量路由到负责这些 IP 的正确节点这一问题。这属于网络特定范畴，但查看具体示例将有助于深入了解相关问题。例如，在 AWS 中，亚马逊维护了一个用于 Kubernetes 的容器网络插件，该插件允许使用容器网络接口 (CNI) 插件在 Amazon VPC 环境中实现节点到节点的网络通信。

容器网络接口 (CNI) 提供了一个通用的 API，用于将容器连接到外部网络。作为开发人员，我们希望了解 Pod 如何使用 IP 地址与网络通信，并且希望此操作的机制是透明的。AWS 开发的 CNI 插件旨在满足这些需求，同时通过 AWS 提供的现有 VPC、IAM 和安全组功能，提供一个安全且易于管理的环境。该解决方案是使用弹性网络接口。

在 EC2 中，每个实例都绑定到一个弹性网络接口 (ENI)，所有 ENI 都连接在同一个 VPC 内——ENI 之间无需额外配置即可相互访问。默认情况下，每个 EC2 实例都部署了一个 ENI，但您可以根据需要创建多个 ENI 并将其部署到 EC2 实例。适用于 Kubernetes 的 AWS CNI 插件利用了这种灵活性，为部署到节点的每个 Pod 创建一个新的 ENI。由于 VPC 内的 ENI 已在现有​​的 AWS 基础设施中连接，因此每个 Pod 的 IP 地址都可以在 VPC 内直接寻址。当 CNI 插件部署到集群时，每个节点（EC2 实例）都会创建多个弹性网络接口，并为这些实例分配 IP 地址，从而为每个节点形成一个 CIDR 块。部署 Pod 时，一个作为 DaemonSet 部署到 Kubernetes 集群的小型二进制文件会接收来自节点本地kubelet进程的任何将 Pod 添加到网络的请求。该二进制文件从节点的可用以太网接口 (ENI) 池中选择一个可用的 IP 地址，并通过在 Linux 内核中配置虚拟以太网设备和网桥，将其分配给 Pod，具体操作方式与在同一节点内配置 Pod 时所述相同。完成此操作后，Pod 流量即可在集群内的不同节点之间路由。

5. Pod到服务的联网#

我们已经展示了如何在 Pod 及其关联的 IP 地址之间路由流量。这种方法在处理变更之前效果很好。Pod 的 IP 地址并不持久，会随着规模扩容或缩减、应用程序崩溃或节点重启而出现或消失。这些事件都可能导致 Pod 的 IP 地址在没有任何预警的情况下发生变化。Kubernetes内置了服务机制来解决这个问题。

Kubernetes Service管理一组 Pod 的状态，允许您跟踪随时间动态变化的一组 Pod IP 地址。Service 作为 Pod 的抽象层，为一组 Pod IP 地址分配一个虚拟 IP 地址。任何发往 Service 虚拟 IP 地址的流量都将被路由到与该虚拟 IP 地址关联的一组 Pod。这使得与 Service 关联的 Pod 集合可以随时更改——客户端只需知道 Service 的虚拟 IP 地址，该地址不会改变。

创建新的 Kubernetes 服务时，系统会为您创建一个新的虚拟 IP 地址（也称为集群 IP 地址）。集群内任何指向该虚拟 IP 地址的流量都会被负载均衡到与该服务关联的后端 Pod 集合。实际上，Kubernetes 会自动创建并维护一个分布式集群内负载均衡器，将流量分配到服务关联的健康 Pod。接下来，我们将详细了解其工作原理。

5.1 netfilter 和 iptables#

为了在集群内实现负载均衡，Kubernetes 依赖于 Linux 内置的网络框架——Netfilter。Netfilternetfilter是 Linux 提供的一个框架，它允许以自定义处理程序的形式实现各种网络相关操作。Netfilter 提供数据包过滤、网络地址转换和端口转换等多种功能和操作，这些功能既能引导数据包在网络中传输，也能阻止数据包到达计算机网络中的敏感位置。

iptablesiptables 是一个用户空间程序，它提供了一个基于表格的系统，用于定义使用 netfilter 框架操作和转换数据包的规则。在 Kubernetes 中，iptables 规则由 kube-proxy 控制器配置，该控制器会监视 Kubernetes API 服务器的变更。当 Service 或 Pod 的虚拟 IP 地址或 IP 地址发生变更时，iptables 规则会更新，以便将指向 Service 的流量正确路由到相应的 Pod。iptables 规则会监视发往 Service 虚拟 IP 的流量，一旦匹配到流量，就会从可用 Pod 集合中随机选择一个 Pod IP 地址，并将数据包的目标 IP 地址从 Service 的虚拟 IP 更改为所选 Pod 的 IP 地址。随着 Pod 的启动或关闭，iptables 规则集也会更新以反映集群状态的变化。换句话说，iptables 在本地实现了负载均衡，将指向 Service IP 的流量路由到实际 Pod 的 IP 地址。

在返回路径上，IP 地址来自目标 Pod。在这种情况下，iptables 会再次重写 IP 头部，将 Pod 的 IP 地址替换为 Service 的 IP 地址，以便 Pod 认为它始终只与 Service 的 IP 地址通信。

5.2 IPVS#

Kubernetes 最新版本 (1.11) 引入了集群内负载均衡的第二种方案：IPVS。IPVS（IP 虚拟服务器）同样基于 netfilter 构建，并将传输层负载均衡作为 Linux 内核的一部分实现。IPVS 集成到 LVS（Linux 虚拟服务器）中，运行在主机上，充当真实服务器集群前端的负载均衡器。IPVS 可以将基于 TCP 和 UDP 的服务请求定向到真实服务器，并将真实服务器的服务显示为位于同一 IP 地址上的虚拟服务。这使得 IPVS 非常适合 Kubernetes 服务。

在声明 Kubernetes Service 时，您可以指定集群内负载均衡是使用 iptables 还是 IPVS。IPVS 专为负载均衡而设计，并使用更高效的数据结构（哈希表），与 iptables 相比，其扩展性几乎不受限制。使用 IPVS 创建负载均衡的 Service 时，会发生以下三件事：在节点上创建一个虚拟的 IPVS 接口；将 Service 的 IP 地址绑定到该虚拟 IPVS 接口；并为每个 Service 的 IP 地址创建 IPVS 服务器。

未来，IPVS 有望成为集群内负载均衡的默认方法。此变更仅影响集群内负载均衡，在本指南的其余部分，您可以安全地将 iptables 替换为 IPVS 来进行集群内负载均衡，而不会影响后续讨论。现在，让我们来看看数据包在集群内负载均衡服务中的生命周期。

5.3 数据包的生命周期：从 Pod 到服务#

在 Pod 和 Service 之间路由数据包时，其路径与之前相同。数据包首先通过eth0 连接到 Pod 网络命名空间的接口离开 Pod (1)。然后，它经过虚拟以太网设备到达网桥 (2)。网桥上运行的 ARP 协议不知道 Service 的存在，因此它会通过默认路由转发数据包 ( eth03)。但在这里，情况有所不同。在被网桥接收之前eth0，数据包会先经过 iptables 过滤。iptables 接收到数据包后，会使用 kube-proxy 在节点上根据 Service 或 Pod 事件安装的规则，将数据包的目标地址从 Service IP 重写为特定的 Pod IP (4)。现在，数据包的目标地址是 Pod 4，而不是 Service 的虚拟 IP。iptablesconntrack利用 Linux 内核的实用程序来记住所做的 Pod 选择，以便将未来的流量路由到同一个 Pod（除非发生任何扩容事件）。本质上，iptables 直接在节点上实现了集群内负载均衡。然后流量通过我们已经研究过的 Pod 到 Pod 路由流向 Pod（5）。

5.4 数据包的生命周期：服务至 Pod#

接收到此数据包的 Pod 会做出响应，将源 IP 标识为自身 IP，目标 IP 标识为最初发送该数据包的 Pod (1)。数据包进入节点后，会经过 iptables，iptables 会conntrack记住之前的选择，并将数据包的源 IP 重写为服务的 IP，而不是 Pod 的 IP (2)。之后，数据包会通过网桥到达与 Pod 命名空间配对的虚拟以太网设备 (3)，然后到达 Pod 的以太网设备，正如我们之前看到的 (4)。

5.5 使用 DNS#

Kubernetes 可以选择使用 DNS，这样就无需将 Service 的集群 IP 地址硬编码到应用程序中。Kubernetes DNS 作为常规 Kubernetes Service 运行在集群上。它配置 kubelets每个节点上的 DNS 服务，以便容器使用 DNS 服务的 IP 地址来解析 DNS 名称。集群中定义的每个 Service（包括 DNS 服务器本身）都会被分配一个 DNS 名称。DNS 记录会将 DNS 名称解析为 Service 的集群 IP 地址或 Pod 的 IP 地址，具体取决于您的需求。SRV 记录用于指定运行 Service 的特定命名端口。

DNS Pod 由三个独立的容器组成：

  • kubedns监视 Kubernetes 主节点的服务和端点的变化，并维护内存中的查找结构以处理 DNS 请求。
  • dnsmasq：添加了 DNS 缓存以提高性能。
  • sidecar：提供一个单一的健康检查端点，用于对dnsmasq和执行健康检查kubedns。

DNS Pod 本身以 Kubernetes Service 的形式对外暴露，并分配一个静态集群 IP 地址。该 IP 地址在启动时传递给每个正在运行的容器，以便每个容器都能解析 DNS 条目。DNS 条目的解析通过kubedns维护内存中 DNS 表示的系统完成。etcd 后端存储系统用于存储集群状态，并kubedns使用一个库将etcd键值存储转换为 DNS 条目，以便在必要时重建内存中 DNS 查找结构的状态。

CoreDNS 的工作原理与 DNS 类似kubedns，但它采用插件架构，因此更加灵活。从 Kubernetes 1.11 开始，CoreDNS 已成为 Kubernetes 的默认 DNS 实现。

6.互联网服务网络#

到目前为止，我们已经了解了Kubernetes 集群内部的流量路由方式。这固然很好，但遗憾的是，将应用程序与外部世界隔离并不能帮助实现任何销售目标——在某些时候，您肯定希望将服务暴露给外部流量。这种需求凸显了两个相关的问题：(1) 如何将流量从 Kubernetes 服务发送到互联网，以及 (2) 如何将流量从互联网发送到 Kubernetes 服务。本节将依次讨论这两个问题。

6.1 出口——将流量路由到互联网#

将节点流量路由到公共互联网取决于网络的具体情况，并且实际上取决于您的网络如何配置以发布流量。为了使本节内容更加具体，我将使用 AWS VPC 来讨论具体细节。

在 AWS 中，Kubernetes 集群运行在虚拟私有云 (VPC) 内，每个节点都被分配一个私有 IP 地址，该地址只能从 Kubernetes 集群内部访问。为了使流量能够从集群外部访问，您需要将一个互联网网关连接到您的 VPC。互联网网关有两个作用：一是为 VPC 路由表中可路由到互联网的流量提供一个目标；二是为所有已分配公有 IP 地址的实例执行网络地址转换 (NAT)。NAT 转换负责将节点内部的、仅供集群内部使用的私有 IP 地址转换为可在公有互联网上访问的外部 IP 地址。

有了互联网网关，虚拟机就可以自由地将流量路由到互联网。但是，这里存在一个小问题。Pod 拥有自己的 IP 地址，该地址与托管 Pod 的节点的 IP 地址不同，而互联网网关的 NAT 转换只能处理虚拟机的 IP 地址，因为它并不知道哪些 Pod 运行在哪些虚拟机上——网关不具备容器感知能力。让我们再次看看 Kubernetes 是如何使用 iptables 来解决这个问题的。

6.1.1 数据包的生命周期：从节点到互联网#

在下图中，数据包源自 Pod 的命名空间 (1)，并经过连接到根命名空间 (2) 的 veth 对。进入根命名空间后，由于数据包上的 IP 地址与连接到网桥的任何网段都不匹配，因此数据包会从网桥转移到默认设备。在到达根命名空间的以太网设备 (3) 之前，iptables 会对数据包进行源地址转换 (3)。在这种情况下，数据包的源 IP 地址是一个 Pod，如果我们保留 Pod 作为源地址，互联网网关会拒绝该数据包，因为网关的 NAT 功能只能识别连接到虚拟机的 IP 地址。解决方案是让 iptables 执行源地址转换 (NAT)，即更改数据包的源地址，使数据包看起来像是来自虚拟机而不是 Pod。有了正确的源 IP 地址后，数据包就可以离开虚拟机 (4) 并到达互联网网关 (5)。互联网网关会再次执行 NAT，将源 IP 地址从虚拟机内部 IP 重写为外部 IP。最终，数据包将到达公共互联网 (6)。返回途中，数据包沿原路返回，任何源 IP 地址的修改都会被撤销，以便系统的每一层都能接收到它能够理解的 IP 地址：节点或虚拟机级别的虚拟机内部地址，以及 Pod 命名空间内的 Pod IP 地址。

6.2 Ingress — 将互联网流量路由到 Kubernetes#

入口（即如何将流量引入集群）是一个出乎意料的棘手问题。当然，这取决于你运行的网络，但一般来说，入口管理分为两种解决方案，分别作用于网络堆栈的不同部分：（1）服务负载均衡器和（2）入口控制器。

6.2.1 第 4 层入口：负载均衡器#

创建 Kubernetes 服务时，您可以选择性地指定一个与之配套的负载均衡器。负载均衡器的实现由云控制器提供，该控制器能够为您的服务创建负载均衡器。服务创建完成后，它会将负载均衡器的 IP 地址发布到其他服务器。作为最终用户，您可以将流量定向到负载均衡器，从而开始与您的服务通信。

借助 AWS，负载均衡器能够识别目标组内的节点，并将流量均衡分配到集群中的所有节点。流量到达某个节点后，之前在集群中为您的服务配置的 iptables 规则将确保流量到达您感兴趣的服务的 Pod。

6.2.2 数据包的生命周期：负载均衡器到服务#

让我们来看看它在实践中是如何运作的。部署服务后，您使用的云服务提供商会为您创建一个新的负载均衡器 (1)。由于负载均衡器不感知容器，流量到达负载均衡器后会被分配到组成集群的各个虚拟机 (2)。每个虚拟机上的 iptables 规则会将来自负载均衡器的入站流量定向到正确的 Pod (3)——这些 iptables 规则与之前在服务创建过程中设置的规则相同。Pod 向客户端返回的响应会包含 Pod 的 IP 地址，但客户端需要负载均衡器的 IP 地址。conntrack正如我们之前看到的，iptables 用于在返回路径上正确重写 IP 地址。

下图展示了位于三个虚拟机（托管您的 Pod）前端的网络负载均衡器。入站流量 (1) 被定向到您的 Service 的负载均衡器。负载均衡器收到数据包 (2) 后，会随机选择一个虚拟机。在本例中，我们特意选择了没有运行任何 Pod 的虚拟机：虚拟机 2 (3)。此时，运行在该虚拟机上的 iptables 规则会利用集群内部通过 kube-proxy 安装的负载均衡规则，将数据包定向到正确的 Pod。iptables 会执行正确的 NAT 转换，并将数据包转发到正确的 Pod (4)。

6.2.3 第 7 层入口：入口控制器#

第七层网络入口（Ingress）运行在网络栈的 HTTP/HTTPS 协议范围内，并构建于 Service 之上。启用 Ingress 的第一步是NodePort在 Kubernetes 中使用 Service 类型为 Service 打开一个端口。如果将 Service 的类型字段设置为 NodePort，Kubernetes 主节点将从您指定的端口范围内分配一个端口，并且每个节点都会将该端口（每个节点上的端口号相同）代理到您的 Service。也就是说，任何指向节点端口的流量都将使用 iptables 规则转发到 Service。这种 Service 到 Pod 的路由遵循与我们之前讨论过的从 Service 到 Pod 的流量路由相同的内部集群负载均衡模式。

要将节点的端口暴露给互联网，可以使用 Ingress 对象。Ingress 是一个更高级别的 HTTP 负载均衡器，它将 HTTP 请求映射到 Kubernetes 服务。Ingress 的具体实现方式取决于 Kubernetes 云提供商控制器的实现方式。与四层网络负载均衡器类似，HTTP 负载均衡器只能识别节点 IP 地址（而非 Pod IP 地址），因此流量路由同样利用了 kube-proxy 在每个节点上安装的 iptables 规则所提供的内部负载均衡。

在 AWS 环境中，ALB Ingress 控制器使用 Amazon 的 Layer 7 应用程序负载均衡器 (ALB) 提供 Kubernetes Ingress 服务。下图详细说明了此控制器创建的 AWS 组件，并展示了 Ingress 流量从 ALB 到 Kubernetes 集群的路由路径。

创建完成后，(1) Ingress 控制器会监听来自 Kubernetes API 服务器的 Ingress 事件。当找到符合其要求的 Ingress 资源时，它会开始创建 AWS 资源。AWS 使用应用程序负载均衡器 (ALB) (2) 来管理 Ingress 资源。负载均衡器与目标组协同工作，目标组用于将请求路由到一个或多个已注册的节点。(3) AWS 会为 Ingress 资源描述的每个唯一 Kubernetes 服务创建目标组。(4) 监听器是 ALB 进程，它会使用您配置的协议和端口检查连接请求。Ingress 控制器会为 Ingress 资源注解中详述的每个端口创建监听器。最后，会为 Ingress 资源中指定的每个路径创建目标组规则。这确保了发往特定路径的流量被路由到正确的 Kubernetes 服务 (5)。

6.2.4 数据包的生命周期：从入口到服务#

数据包流经 Ingress 的生命周期与流经 LoadBalancer 的生命周期非常相似。主要区别在于，Ingress 能够感知 URL 的路径（从而可以根据路径将流量路由到相应的服务），并且 Ingress 与节点之间的初始连接是通过节点上为每个服务暴露的端口建立的。

让我们来看看它在实践中是如何运作的。部署服务后，您使用的云服务提供商会为您创建一个新的 Ingress 负载均衡器 (1)。由于负载均衡器不感知容器，流量到达负载均衡器后，会通过您服务所通告的端口分发到组成集群的各个虚拟机 (2)。每个虚拟机上的 iptables 规则会将来自负载均衡器的入站流量定向到正确的 Pod (3)——正如我们之前看到的。Pod 向客户端返回的响应将包含 Pod 的 IP 地址，但客户端需要负载均衡器的 IP 地址。iptables conntrack用于在返回路径上正确重写 IP 地址，正如我们之前看到的。

第七层负载均衡器的一个优势在于它们支持 HTTP 协议，因此能够识别 URL 和路径。这使您可以按 URL 路径对服务流量进行分段。此外，它们通常还会在X-Forwarded-ForHTTP 请求头中提供原始客户端的 IP 地址。

8 词汇表#

Kubernetes 依赖于多种现有技术来构建一个功能完善的集群。全面探讨每项技术超出了本指南的范围，但本节将对每项技术进行足够详细的描述，以便您能够理解后续的讨论。您可以随意浏览本节内容，也可以完全跳过，或者在遇到困惑或需要复习时随时查阅。

二层网络#

第二层是数据链路层，提供节点到节点的数据传输。它定义了在两个物理连接的设备之间建立和终止连接的协议，也定义了它们之间的流量控制协议。

第四层网络#

传输层通过流量控制来保证特定链路的可靠性。在 TCP/IP 协议中，该层指的是用于在不可靠网络上交换数据的 TCP 协议。

第七层网络#

应用层是最接近最终用户的层，这意味着应用层和用户都直接与软件应用程序交互。该层与实现了通信组件的软件应用程序进行交互。通常，第七层网络指的是HTTP协议。

NAT — 网络地址转换#

网络地址转换(NAT)是一种将一个地址空间重新映射到另一个地址空间的 IP 层技术。这种映射是通过在数据包通过流量路由设备传输时，修改数据包 IP 报头中的网络地址信息来实现的。

基本的NAT（网络地址转换）就是将一个IP地址映射到另一个IP地址。更常见的情况是，NAT用于将多个私有IP地址映射到一个公网IP地址。通常，本地网络使用私有IP地址空间，网络上的路由器会被分配一个私有地址。然后，路由器通过公网IP地址连接到互联网。当流量从本地网络传输到互联网时，每个数据包的源地址都会从私有地址转换为公网地址，使请求看起来像是直接来自路由器。路由器会维护连接跟踪，以便将响应转发到本地网络上正确的私有IP地址。

NAT 的另一个好处是允许大型私有网络使用单个公共 IP 地址连接到互联网，从而节省公共 IP 地址的数量。

SNAT — 源网络地址转换#

SNAT 指的是一种 NAT 过程，它会修改 IP 数据包的源地址。这是上述 NAT 的典型行为。

DNAT — 目标网络地址转换#

DNAT 是一种 NAT 过程，它会修改 IP 数据包的目标地址。DNAT 用于将私有网络中的服务发布到公网 IP 地址。

网络命名空间#

在网络中，每台机器（无论是物理机还是虚拟机）都有一个以太网设备（我们称之为“以太网eth0”）。所有进出机器的流量都与该设备关联。实际上，Linux 将每个以太网设备与一个网络命名空间关联起来——它是整个网络协议栈的逻辑副本，拥有自己的路由、防火墙规则和网络设备。最初，所有进程共享来自 init 进程的同一个默认网络命名空间，称为根命名空间。默认情况下，进程会继承其父进程的网络命名空间，因此，如果您不做任何更改，所有网络流量都将通过为根网络命名空间指定的以太网设备流动。

veth — 虚拟以太网设备对#

计算机系统通常由一个或多个网络设备（例如 eth0、eth1 等）组成，这些设备与物理网络适配器关联，后者负责将数据包发送到物理线路上。Veth 设备是虚拟网络设备，它们总是成对创建并互连。它们可以充当网络命名空间之间的隧道，从而建立与另一个命名空间中的物理网络设备的桥梁，也可以用作独立的网络设备。您可以将 Veth 设备视为设备之间的虚拟跳线——从一端输入的数据将从另一端输出。

桥 — 网络桥#

网络桥接器是一种将多个通信网络或网段聚合为单一网络的设备。桥接可以将两个独立的网络连接起来，使其如同一个单一网络。为了优化性能，桥接器使用内部数据结构来记录每个数据包的发送位置。

CIDR — 无类别域间路由#

CIDR 是一种分配 IP 地址和执行 IP 路由的方法。在 CIDR 中，IP 地址由两部分组成：网络前缀（用于标识整个网络或子网）和主机标识符（用于指定该网络或子网上主机的特定接口）。CIDR 使用 CIDR 表示法来表示 IP 地址，其中地址或路由前缀后面会添加一个后缀，该后缀指示前缀的位数，例如 IPv4 的 192.0.2.0/24。IP 地址属于 CIDR 块，如果地址的前 n 位与 CIDR 前缀相同，则称该地址属于该 CIDR 块。

CNI — 容器网络接口#

CNI（容器网络接口）是云原生计算基金会的一个项目，它包含一个规范和一系列库，用于编写插件以配置 Linux 容器中的网络接口。CNI 只关注容器的网络连接以及在容器删除时释放已分配的资源。

VIP — 虚拟IP地址#

虚拟 IP 地址（VIP）是一种软件定义的 IP 地址，它不对应于实际的物理网络接口。

netfilter — Linux 数据包过滤框架#

netfilter 是 Linux 中的数据包过滤框架。实现该框架的软件负责数据包过滤、网络地址转换 (NAT) 和其他数据包处理操作。

netfilter、ip_tables、连接跟踪（ip_conntrack、nf_conntrack）和 NAT 子系统共同构成了该框架的主要部分。

iptables — 数据包篡改工具#

iptables 是一个程序，它允许 Linux 系统管理员配置网络过滤器及其存储的链和规则。IP 表中的每条规则都由若干分类器（iptables 匹配项）和一个关联的操作（iptables 目标）组成。

conntrack — 连接跟踪#

conntrack 是一个基于 Netfilter 框架构建的工具，用于处理连接跟踪。连接跟踪允许内核跟踪所有逻辑网络连接或会话，并将每个连接或会话的数据包定向到正确的发送方或接收方。NAT 依赖此信息以相同的方式转换所有相关数据包，而 iptables 可以利用此信息充当有状态防火墙。

IPVS — IP虚拟服务器#

IPVS 作为 Linux 内核的一部分，实现了传输层负载均衡。

IPVS 是一款类似于 iptables 的工具。它基于 Linux 内核的 netfilter 钩子函数，但使用哈希表作为底层数据结构。这意味着，与 iptables 相比，IPVS 重定向流量的速度更快，同步代理规则的性能更佳，并且提供了更多负载均衡算法。

DNS — 域名系统#

域名系统（DNS）是一个去中心化的命名系统，用于将系统名称与IP地址关联起来。它将域名转换为数字IP地址，以便定位计算机服务。
